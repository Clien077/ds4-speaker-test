Tests whether the **built-in speaker (and the 3.5 mm headphone jack)** of a PlayStation DualShock 4 controller works,
**supports arbitrary custom test audio** (wav / mp3 / flac / ogg / m4a…), and also ships standard test signals such as sweeps, noise, and channel callouts.

The tool exposes two completely different paths, because **the DS4's built-in speaker has no audio device at all under Windows**:

| Path | Description | Command |
|---|---|---|
| **HID + SBC (the real built-in speaker)** | Follows Sony's private PS4 protocol and packs SBC audio into HID output reports sent straight to the controller | `--bt` |
| Windows audio endpoint (3.5 mm headphone jack) | The controller's USB Audio Class / Bluetooth audio endpoint; drives the headphone jack only, never the built-in speaker | default / `--wired` |

### Can the built-in speaker be tested over a wired (USB) connection?

**What matters is not "Bluetooth versus USB", but whether this HID interface exposes the audio reports (0x14/0x17):**

| Connection | Audio reports | Built-in speaker testable? |
|---|---|---|
| Direct Bluetooth | Yes (0x11–0x19, 547 bytes) | ✅ Yes |
| **Sony's official USB wireless adapter CUH-ZWA1** (plugs into a USB port, so it also counts as "wired") | Yes | ✅ Yes |
| **Controller connected directly with a USB data cable** | No (largest output report is only **32 bytes**, and only 0x05) | ❌ Physically impossible |

Measured evidence with a direct USB data cable connection (`--wired` runs this diagnostic automatically):

```
Output reports: 0x05, largest output report 32 bytes
Write 0x11(78B)   → failed err=87 invalid parameter
Write 0x14(270B)  → failed err=87 invalid parameter
Write 0x17(462B)  → failed err=87 invalid parameter
Play back through the controller's audio endpoint one by one: only a "pop" when the stream opens; sustained audio energy is at the same level as the noise floor (user confirmed silence when held to the ear)
```

**The 270/462-byte audio reports simply cannot be sent over a USB data cable connection**, and the controller firmware
exposes no audio path to the built-in speaker at all (Windows only recognizes its 3.5 mm headphone jack as an audio device)
— this is not something software can work around.

So `--wired` does what is **actually possible** on the current connection:

```bat
python ds4_speaker_test.py --wired                    :: diagnostics + light bar/rumble self-test + automatic 3.5 mm headphone jack test
python ds4_speaker_test.py --wired-control-test       :: light bar/rumble self-test only (USB 0x05 report)
python ds4_speaker_test.py --wired --file test.mp3    :: send custom audio to the headphone jack
python ds4_speaker_test.py --bt-list                  :: list controller interfaces and mark whether each can drive the built-in speaker
```

The GUI decides automatically: with a data cable attached it switches to the "Windows audio endpoint" path and explains why in the log.
The "☀ Light bar/rumble self-test" button at the top works on both connections (Bluetooth uses the 0x11 report, USB uses the 0x05 report).

## 1. Why Windows audio devices cannot be used to test the built-in speaker

- The `Headphones / Microphone (Wireless Controller)` device in Windows is **USB Audio Class (UAC)** and goes through the
  controller's **3.5 mm headphone jack**; over Bluetooth, if the controller is configured only as a HID device, none of these
  endpoints even appear.
- **The DS4 (DualShock 4) has no built-in microphone** (the one with a microphone array is the PS5's DualSense); that
  `Microphone (…Wireless Controller)` entry is the headset microphone on the headphone jack, so it is inevitably silent
  unless a headset with a mic is plugged in.
- The **built-in speaker** is driven by the PS4 via **SBC-encoded audio** stuffed into Bluetooth HID output reports (a private
  protocol, not A2DP). Reference implementations: [nefarius/DS4AudioStreamer](https://github.com/nefarius/DS4AudioStreamer),
  [ds4drv #76](https://github.com/chrippa/ds4drv/issues/76) and its
  [play.py](https://gist.github.com/a1ien/e8a82f71c13ae54f886fbf94f0606073).

### Key parameters mined from the raw protocol (all aligned and verified on real hardware in this tool)

| Item | Value | Notes |
|---|---|---|
| **0x11 control report** | 78 bytes, **must be sent first** | Without it the built-in speaker never makes a sound |
| ├ `[2]` | **0x20** = `audio_control` | **Enables the audio path**. Writing 0xA2 here produces complete silence (0xA2 belongs only to byte 3 of the audio report) |
| ├ `[21..25]` | `0x43,0x43,0x00,volume%,0x85` | Volume is a **percentage** (0-100), and it must be followed by `0x85` |
| └ `[74..77]` | CRC32 (seed 0xA2, over the first 74 bytes) | Easy to place incorrectly when writing it by hand |
| **Audio report** | **0x17** (4 frames/462B) or **0x14** (2 frames/270B) | 4 frames preferred; use 0x14 when only 1–3 frames remain |
| ├ `[2]` | **0xA0** | 0xA2 produces silence |
| ├ `[5]` | **0x02** = built-in speaker, `0x24` = 3.5 mm headphone jack | Taken from PS4 packet captures |
| └ CRC32 | Placed at **the end of the report's actual length** | 0x17→`[458:462]`, 0x14→`[266:270]` |
| **Write length** | **547 bytes** (the HID collection's maximum output report length) | Writing only 462/270 bytes gets rejected by the driver or dropped by the controller; zero-pad to the full length |
| SBC encoding | 32 kHz / 2 channels, ffmpeg defaults (8 subbands, 16 blocks, joint stereo, bitpool 26 → **65-byte frames**) | Frame length is determined by the frame header, and the controller parses frames by their header |
| Handshake | First send a 0x11 with rumble (the controller buzzes once), then send the real one | The buzz means the HID channel + audio path are ready |
| Cadence | One 4-frame report every 16 ms (= 250 frames/second) | Keeps pace with real-time playback |

> These parameters were calibrated against your `F:\Program Files (x86)\DS4扬声器测试` (three-way cross-check: PS4 packet capture
> + Linux `hid-playstation.c` + Unity) and then **objectively re-verified by capturing audio through a microphone**:
> the reference tool's playback-window RMS was -37.8 dBFS against a -65.3 dBFS noise floor (**+27.6 dB**);
> with the parameters above, this tool's playback-window RMS is ≈ -22 dBFS with a spectral similarity of 0.88–0.9.

## 2. Quick start

```bat
:: Double-click run.bat to open the GUI, or:
python ds4_speaker_test.py                       :: GUI (defaults to the Bluetooth built-in speaker)
python ds4_speaker_test.py --bt-list             :: show controller HID interfaces and connection type (Bluetooth/USB)
python ds4_speaker_test.py --bt-selftest         :: offline Bluetooth path self-test (no sound, nothing sent)
python ds4_speaker_test.py --bt-control-test     :: verify the HID path with the light bar + rumble (visible confirmation)

:: Bluetooth built-in speaker (the controller must be connected over Bluetooth)

python ds4_speaker_test.py --bt --loopback-test --signal tone --duration 3

python ds4_speaker_test.py --list
python ds4_speaker_test.py --signal sweep --device 26

python ds4_speaker_test.py --selftest            :: offline self-test
```

## 3. Why the Bluetooth path requires a Bluetooth connection

Built-in speaker audio can only reach the controller over **Bluetooth HID** (this path does not work over USB).

- Hold **Share + PS** on the controller to enter pairing mode, then add `Wireless Controller` in Windows Bluetooth settings;
- Use `--bt-list` to confirm **BT** is shown;
- If DS4Windows is running, exit it first so it does not grab the HID device.

## 4. Graphical interface

1. **Output path and device**: choose "Bluetooth built-in speaker (HID + SBC)" or "Windows audio endpoint";
   in Bluetooth mode you can pick the controller HID's **report path byte** (default 0x24, verified working).
2. **Test audio**: a built-in signal, or a **custom audio file** (browse to select, with optional start position and duration).
3. **Playback settings**: volume (-40 ~ +20 dB), channel routing (both / left only / right only), loop playback.
4. **Real-time level meter**: in Bluetooth mode it shows stream progress; in audio-endpoint mode it shows per-channel peaks and clip counts.
5. **Loopback self-test**: play once → record it back with a microphone → automatic verdict, and you can save the recording as a WAV.

## 5. Built-in test signals

| Name | Purpose |
|---|---|
| `tone` | Single tone (1 kHz by default, changeable with `--freq`) — the simplest "is there any sound" check |
| `sweep` | 20 Hz → 20 kHz logarithmic sweep: listen for breakup, noise, and frequency-response gaps |
| `sweep_speech` | 200 Hz → 6 kHz: the speech band, for judging volume and clarity |
| `white` / `pink` | White noise / pink noise: full-band stress test |
| `channels` | Left → right → both: channel callout (for testing the headphone jack) |
| `polarity` | In phase / out of phase: low-frequency phase check |
| `dtmf` | DTMF 1-0: fixed frequency combinations for quickly judging frequency-response distortion |
| `silence` | Silence: verifies only whether the link can open (no sound) |
| `all` | Full test sequence (about 32 seconds, plays every item in order) |

## 7. Loopback self-test (automatic verdict)

Flow: **record 0.5 s first → play the test audio → record 1 s more → analyze**.

Criteria (only the interval that "should be making sound" is used, and it is compared against the noise floor before and after streaming):

1. **Signal-to-noise ratio**: if the playback window is less than 6 dB above the noise floor, the verdict is `SILENT` immediately (this step
   matters: spectral similarity cannot discriminate a "noise floor only" recording, which once caused a false PASS);
2. **Capture level**: a peak below -50 dBFS is judged `SILENT`;
3. **Spectral similarity** (cosine similarity over 80 Hz ~ 8 kHz) and **envelope correlation** (which can also estimate delay for signals with dynamics).

| Verdict | Meaning |
|---|---|
| `PASS` | Sound is normal and closely matches the test audio |
| `WEAK` | Sound is present but matches poorly (low volume / distortion / high noise floor) |
| `CLIPPED` | Severe clipping, volume too high |
| `SILENT` | Almost no sound (volume too low / wrong path byte / wrong microphone selected) |
| `UNCLEAR` | Sound was recorded but does not resemble the test audio (usually just ambient noise) |

Exit codes: `0` = PASS, `1` = WEAK/UNCLEAR, `2` = SILENT/CLIPPED.

**The DS4's built-in speaker is inherently very quiet**; in a quiet room, hold the controller to your ear or bring a microphone within 10 cm to verify.

## 8. What to do about audio dropouts (stuttering)

The DS4's Bluetooth HID audio path **will occasionally drop audio by nature**: the people who reverse-engineered it
([ds4drv #76](https://github.com/chrippa/ds4drv/issues/76),
[that pvsm article](https://www.pvsm.ru/python/124992)) all noted "the sound has periodic small stutters, cause unknown", and nobody ever fixed it.

This tool does three things to eliminate most of the stuttering:

| Measure | Notes |
|---|---|
| Pre-pack all reports | Streaming then only waits and writes; per-packet Python cost drops from 0.05 ms to 0.01 ms, removing GC jitter |
| Pre-fill buffer `--bt-lead` (6 reports ≈ 96 ms by default) | Sends several reports back-to-back at playback start to pad the controller's jitter buffer and absorb Bluetooth link jitter |
| Periodic control refresh `--bt-control-every` (20 by default) | Real PS4 hardware keeps refreshing the control state inside the audio stream (0x15/0x19); with no refresh at all, the controller's audio path occasionally "starves" |

**Measurements (the same steady 1 kHz tone, with dropouts counted from microphone capture)**:

| Implementation | Share of time with gaps ≥20 ms |
|---|---|
| Reference tool (the one on your machine) | **20.1%** (longest single gap 1.49 seconds) |
| This tool, `lead=0` | 4.1% |
| **This tool, `lead=6` (default)** | **3.5%** |

Host-side timing is nearly ideal (16.000 ms send interval, 0.2 ms write, 0 late reports), so the residual dropouts come from the Bluetooth link itself. If it still stutters:

1. `--bt-lead 12` or `--bt-lead 20` (a larger pre-fill, at the cost of slightly more latency);
2. `--bt-speed 1.02` (thickens the padding gradually; too high overflows and makes things worse);
3. `--bt-frames 2` (switch to the smaller 270-byte report, so a single drop loses only 8 ms and stutters less noticeably);
4. **Reduce 2.4 GHz interference**: Bluetooth shares the 2.4 GHz band with WiFi and wireless mice — move the 2.4G wireless receiver to another USB port (or away from the controller) and switch WiFi to 5 GHz; this usually helps the most;
5. Keep the controller closer to the computer, with nothing blocking the path.

The GUI also has matching "pre-fill buffer / stream rate / control refresh" inputs so you can tune while listening.

## 9. Packaging as an EXE

Just double-click `build_exe.bat` (checks dependencies → packages → collects everything into `release\`). Artifacts:

| File | Purpose |
|---|---|
| `release\DS4-Speaker-Test\DS4-Speaker-Test.exe` | **Recommended**: folder build, double-click and go. Fast startup (about 1 second), **extracts nothing at runtime**, and cannot fail however it is launched |
| `release\DS4-Speaker-Test-Single.exe` | Single-file build, 52 MB and easy to move around; at startup it extracts itself into **its own directory** (`--runtime-tmpdir .`) |
| `release\DS4-Speaker-Test-CLI.exe` | Single-file command-line build; output can be redirected or scripted |
| `release\USAGE.txt` | Concise instructions for end users |

The EXE bundles ffmpeg (imageio-ffmpeg), PortAudio (sounddevice), pywinusb, and tkinter, so the target machine **needs neither Python nor any dependencies**.

### Why the folder build is recommended

The single-file build must extract 52 MB to a temporary directory on every launch, and that step has two common pitfalls:

1. **Antivirus interference** with the extraction;
2. **Integrity level restrictions**: if the exe is launched from a chat window's "file card" or from a sandboxed environment,
   it runs with a **low integrity token**, while `%TEMP%` is medium integrity — Windows Mandatory Integrity Control (MIC)
   **forbids low-integrity processes from writing upwards**, so it reports `Could not create temporary directory!`
   (the extraction directory's ACL is left with a `Mandatory Label\Low Mandatory Level:(NW)` trace).

The folder build **creates no directories at runtime**, so it is entirely immune to both issues. If you really want the single-file build,
double-click it from an **ordinary Explorer window**, not from a file card in a chat window.

## 10. FAQ

**No sound when streaming over Bluetooth?**
1. Run `--bt-control-test` first: the light bar turns green + rumble means the HID path is fine; if neither reacts, the reports are not
   being accepted (usually another program has taken over the HID device, or the controller is not connected over Bluetooth);
2. Try a different path byte: `--bt-path 0x24` (headphone jack) / `0x00` / `0x03`;
3. Check the controller volume, `--bt-volume 255` (already maximum by default);
4. The DS4's small speaker has limited volume, so verify with it held to your ear; plugging a headset into the controller's headphone jack
   for comparison distinguishes a "path problem" from a "speaker problem".

**Can the Bluetooth path be used while connected over USB?** No — the built-in speaker is Bluetooth-only; `--bt-list` reports when the current connection is USB.

**WASAPI exclusive mode will not open?** Exclusive mode requires the sample rate to match the device's native format; clear the checkbox or specify `--samplerate`.
